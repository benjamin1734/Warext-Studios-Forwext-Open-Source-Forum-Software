# Marketplace Native Purchase Contract (14.04)

## Scope

This sub-step establishes Forwext's first-party cart, checkout and order foundation. It deliberately stops before payment-provider integrations, commissions, seller balances, refunds, digital-license generation, protected downloads or manual-delivery fulfillment.

Those concerns belong to later Marketplace sub-steps and attach to the order/payment/delivery state model defined here.

## Permissions

Native purchasing uses the shared permission engine:

- `marketplace.internal_purchase.use`: seller/listing capability for first-party checkout.
- `marketplace.purchase`: buyer capability for adding eligible listings to cart and checking out.
- `marketplace.order.manage`: staff capability for global order access and authorized lifecycle intervention.

Frontend visibility never substitutes for these backend checks.

Historical buyer/seller order access is ownership-based rather than depending on the user's current purchase/seller capability. Revoking future purchasing rights therefore does not hide already-created records.

## Internal-sale listing setting

Each listing may independently enable or disable native purchase through `forwext_marketplace_internal_sale_settings`.

A listing is currently purchasable only when:

1. it is in the `active` listing state;
2. the buyer is not the seller;
3. the buyer currently has `marketplace.purchase`;
4. the seller currently has `marketplace.internal_purchase.use`;
5. the listing's internal-sale setting is enabled.

Seller permission is re-evaluated at runtime. Revoking the seller capability immediately disables new native purchases without rewriting historical orders.

## Cart

`forwext_marketplace_cart_items` stores at most one row per buyer/listing pair. The service caps a cart at 50 unique listings.

Cart mutations are CSRF-protected in the native PHP frontend. Checkout locks the buyer's cart rows with `FOR UPDATE`.

If a listing becomes unavailable after it was added, the cart does not expose its private/non-public title or price. The stale entry is represented only as unavailable until removed.

## Checkout

Checkout receives a 128-bit lowercase hexadecimal `checkout_key` generated by the server-rendered checkout form.

The checkout service is transactional and idempotent for a buyer/key pair:

1. previously created orders for the same buyer/key are returned immediately;
2. cart rows are locked;
3. the idempotency check is repeated after the lock;
4. every cart listing is revalidated;
5. a single unavailable listing rejects the complete checkout;
6. listings are grouped by seller and currency;
7. one order is created for each seller/currency group;
8. title, price and billing values are snapshotted;
9. order history is appended;
10. the buyer cart is cleared only after all orders were created successfully.

The unique database key `(buyer_user_id, checkout_key, seller_user_id, currency)` provides an additional persistence-level idempotency boundary.

A checkout does not call a payment provider in 14.04. New orders begin as:

- order: `pending`
- payment: `pending`
- delivery: `pending`

## Price and item snapshots

Order items copy:

- listing id;
- title;
- quantity;
- unit price;
- currency;
- line total.

Future listing edits therefore cannot change historical order pricing or item names.

The database repository validates order-id ownership, order/item currency agreement and exact subtotal equality before any order row is inserted. Stored line totals are also recalculated and checked when order items are read.

## Billing and receipt metadata

Checkout snapshots billing data as JSON:

- name / company name;
- email;
- ISO-style two-letter country code;
- optional tax identifier;
- optional address line.

Invalid UTF-8, control characters and oversized values are rejected.

Orders also carry generic `receipt_json` metadata. In 14.04 it records the checkout mode and item count; later invoice/payment/delivery systems may append bounded scalar metadata without redesigning the order schema.

## Order access and IDOR controls

Order detail access is granted only when the actor is:

- the buyer;
- the seller; or
- authorized by `marketplace.order.manage`.

An unrelated user receives the same unavailable/not-found behavior instead of order metadata.

Order managers can list all orders. Ordinary users list only records in which they are buyer or seller.

## Cancellation

Before payment-provider integration, a buyer or order manager may cancel only an order whose order and payment states are both still `pending`.

Cancellation atomically changes:

- order -> `cancelled`
- payment -> `cancelled`
- delivery -> `cancelled`

The change is added to order history and central audit.

## Notifications

Successful order creation dispatches deduplicated in-app notifications to buyer and seller.

Notification failure is fail-open with respect to the already-created durable order: a notification-channel failure must not roll back checkout.

## Migration

Migration `20260919213000_marketplace_native_purchase` adds:

- `forwext_marketplace_internal_sale_settings`
- `forwext_marketplace_cart_items`
- `forwext_marketplace_orders`
- `forwext_marketplace_order_items`
- `forwext_marketplace_order_history`

It also installs conservative permission-template defaults for native purchasing and order management.

## Deployment

The feature is fully available through the first-party native PHP frontend and requires no mandatory Node.js, Redis, worker, WebSocket, Docker or SSH runtime on a normal cPanel installation.
