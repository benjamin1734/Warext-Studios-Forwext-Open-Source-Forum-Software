# 09.03 — Approval / moderation queue

Implemented the shared first-party approval queue required by the master roadmap.

- Added a typed `ApprovalQueueRegistry` and provider contract for current and future moderated content domains.
- Replaced the forum-only workspace source with a shared queue adapter while retaining real forum thread/post data as the first provider.
- Added native `/moderation/approval` queue UX with bounded bulk selection, approve/reject actions and reason codes.
- Reused `moderation.access`, `moderation.manage`, node-scoped forum permissions and the existing same-origin moderation guard.
- Required `forum.view`, the relevant thread/post moderate permission and `forum.moderation.bulk` before forum entries become actionable queue candidates.
- Added first-class thread/post reject moderation actions that persist the existing `rejected` state rather than treating rejection as deletion.
- Added row-locked stale-decision protection so bulk queue approve/reject only mutates content that is still pending.
- Reused the existing moderation audit stream and request-id correlation for per-item and bulk action records.
- Added regression coverage for queue ownership, fail-closed access/manage authorization, deduped provider dispatch, HTML escaping and reject action contracts.
- No database migration or additional cPanel runtime service is required.
