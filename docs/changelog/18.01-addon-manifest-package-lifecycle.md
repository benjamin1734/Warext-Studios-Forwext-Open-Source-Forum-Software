# 18.01 — Add-on manifest/package/lifecycle

Forwext now has the first authoritative third-party add-on package and lifecycle foundation.

- Canonical add-on IDs use `Vendor/AddOn` and extracted packages live under `addons/Vendor/AddOn/`.
- `addon.json` is bounded and fail-closed, uses strict SemVer 2.0 precedence and declares Forwext minimum version, add-on requirements/conflicts and retention policy.
- Package inspection rejects traversal/symlink shapes, enforces entry/per-file/total size limits and computes a deterministic SHA-256 tree checksum.
- Lifecycle supports install, enable, disable, upgrade and uninstall with deterministic dependency/conflict/cycle rules.
- Reinstall of a recorded version requires the identical package checksum; purged data state is preserved rather than silently recreated.
- Enable revalidates current Forwext compatibility and the installed add-on graph.
- Delete-data uninstall requires both a manifest capability and a registered safe purger. Purge executes inside the common audit mutation boundary before lifecycle persistence.
- Persistence uses `forwext_addons` and `forwext_addon_relations`; `addon.manage` is denied by default except for the administrator template.
- The existing shared migration engine now accepts canonical add-on owner IDs for later add-on migrations.
- No Composer/npm/Node/Redis/Docker/Supervisor runtime dependency was added to the normal cPanel profile.
