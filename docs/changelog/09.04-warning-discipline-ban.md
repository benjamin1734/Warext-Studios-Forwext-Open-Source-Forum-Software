# 09.04 — Warning / Discipline / Ban

Implemented the first-party warning, restriction, suspension and ban system required by the binding roadmap.

- Added persistent warning definitions with configurable points, optional point expiry, active state and ordering.
- Added append-only discipline history for warnings, posting/content restrictions, temporary suspensions and temporary/permanent bans.
- Added typed revocation metadata with row-locked stale/double-revoke protection.
- Added granular backend permissions for discipline view, warning issue/definition management, restrictions, bans and revocation.
- Integrated posting/content restrictions into the common permission repository as user-level deny decisions instead of UI-only controls.
- Added authentication availability enforcement for active suspensions/bans to both login and ordinary authenticated-session resolution.
- Kept temporary expiry time-based so access automatically returns when the UTC expiry passes without a required daemon.
- Added `/moderation/discipline` native PHP management UX and real Warning/Ban moderation-workspace sources.
- Added `/account/discipline` so a user with an existing valid session can inspect their own discipline history, active warning points, expiry and appeal reference.
- Added stable `discipline:<action-id>` references plus the `moderation.discipline.appeal_available` domain event for later Support/Ticket integration, without inventing a fake support route.
- Reused moderation audit, notification, request-id and same-origin mutation infrastructure.
- Added migration `20260918003000_discipline_system`; no database reset or additional cPanel runtime service is required.
- Added regression coverage for warning expiry/points, suspension vs permanent ban semantics, self-target refusal, authentication blocking, discipline permission deny overlay and migration registration.
